Why cb_eval:
This pin has llama_context_params.cb_eval. In ggml/src/ggml-backend.cpp, lines 1974-2002, returning true to the ask callback creates a one-node graph view, computes it, synchronizes the backend, then calls the callback again with ask=false. The profiler measures steady_clock time between those two callbacks and never reads tensor data.
A search of this pin's ggml found no GGML_PERF/perf_time/perf_cycles implementation. ggml_graph_print (ggml/src/ggml.c:7963) prints graph shapes and operations but no elapsed times. test-backend-ops would measure isolated synthetic operations rather than this model's actual decode graph. perf was therefore unnecessary.
A persistent four-thread pool matches llama-bench and avoids allocating a disposable threadpool per callback graph. Node-record storage is reserved before measurement. CSV formatting and file output happen after each synchronized step, outside its wall-time interval.

Protocol:
The runner suspends r36llm, saves CPU governors, verifies config.ini remains unchanged, and restores governors and resumes the app in an EXIT trap. It changes no config, backlight, devfreq or installed engine files. Tools and outputs are isolated under /data/r36llm/profile-2026-11-02.
Before every plain/profile/bench process, both thermal zones must reach <=55 C under powersave; the runner then selects performance. Temperatures, frequency and cooling states are sampled every two seconds.
For each model: plain and callback-profile contexts use n_ctx=128, F16 KV, four generation/batch threads, and 128-token batch/ubatch limits. There is one excluded decode warmup, five measured one-token steps at positions 0..4, one excluded prompt warmup and three independent eight-token prompt batches. KV is cleared between prompt trials. Fixed synthetic token IDs, no sampling, match the workload style of llama-bench, not natural-language generation.
A separately cooled patched llama-bench runs -p 8 -n 8 -t 4 -r 3 -o json, using its normal warmup. Generation benchmark time is divided by eight to compare one token. Prompt time is the complete eight-token batch.

Interpretation:
Raw *-nodes.csv contains every node per trial, runtime source type, source tensor name and output shape. *-weights.csv reads original GGUF tensor descriptors (not runtime repacked types), with exact quant type, shape and bytes for every tensor. *-steps.csv includes wall time, sum of timed node intervals and node count.
summary.csv reports median wall/node times and comparison with plain and llama-bench. operations.csv aggregates by ggml op; categories.csv aggregates q/k/v/o, gate/up/down, lm_head, norms, rope, softmax, get_rows and remaining operations. Each aggregate is computed per trial first, then its median is taken. tensors.csv reports median time for each graph tensor/node across trials. Independently taken medians need not sum exactly to the median step.
The callback forces a backend synchronization and a new CPU graph execution for every node. Its intervals include graph dispatch/planning and OpenMP region overhead, not only arithmetic. It can disable cross-node fusion and strongly inflate tiny operations. This is a profile of instrumented execution, not cycle-accurate attribution of uninstrumented inference. Use the paired plain and llama-bench results to judge the total overhead before acting on small-op differences.
