# v0.1.0

## Scope and hardware status

This is the first tagged R36LLM image: a small offline LLM chat OS for an RK3326 handheld with four Cortex-A35 cores and 1 GB RAM. It boots into a framebuffer application with a gamepad keyboard, model picker, preset prompts, chat logs and device settings.

The only targeted board is **`G80CA-MB V1.3-20251212 Panel 8`**. Other R36S boards, panels and clones are not supported by this release.

**Hardware test (2026-11-03), on that board:**

- **Boot chain:** the image's loader area (DDR init, miniloader, BL31/BL32, U-Boot; sectors 64–32767) is **byte-identical** to a working card of this board, rebuilt from source (SHA-256 `ebd1848bd7c2a03620b5ebaf2acfdef0ec0ef2a11ebd1610a45c5ff527508063`).
- **Kernel, device tree and initramfs** of this release were booted on the device from that card: display, gamepad, battery reading, audio device, USB Ethernet/SSH, swap, the chat app and the engine all worked. The default model generated 1.19 tokens/s; the app answered a first question after 12.2 s.
- **First-boot data-partition growth** was not run on hardware. It passed 8 offline scenarios using the release's own ARM64 tools (normal first boot, Windows-created metadata, user files kept, recovery after interruption at each step, too-small disk, changed layout).
- The complete image was therefore not flashed and booted as a whole on a fresh card. Report results with the [board report form](https://github.com/0bAndyWirus/r36llm/issues/new/choose).

**Image SHA-256 (`r36llm.img.xz`):** `c81e17e8f783462cec74d3ad779fa059250ee90008911564a845e7c0f85ef3fd`. This published image was built by the release workflow and compared with the hardware-tested build: the partition table, boot chain, kernel, device trees, `boot.ini` and boot files are byte-identical, and the initramfs differs only in the build timestamps embedded in BusyBox and the app and in the random salt of the (unchanged) default password hash. Details: [release test summary](https://github.com/0bAndyWirus/r36llm/blob/v0.1.0/docs/results/2026-11-03-release-test/summary.txt).

## What's in the image

- Linux 4.4.189, the board device tree and kernel modules built from [`lcdyk0517/arkos.bsp.4.4`](https://github.com/lcdyk0517/arkos.bsp.4.4), using the repository's pinned BSP revision and build configuration.
- U-Boot built from source at commit [`5606e804`](https://github.com/lcdyk0517/Clone-u-boot/commit/5606e804ffe8f9e5427d55c8da04c638f01a9391) of the Clone-u-boot history, with the Linaro GCC 6.3 toolchain and the original build time, reproducing the U-Boot of working cards of this board byte for byte. A display device tree, `rg351v-uboot.dtb`, is built from `scripts/bsp/rg351v-uboot.dts`.
- Rockchip DDR initialization v1.10, miniloader v1.12, BL31 v1.14 and BL32 v1.10 firmware binaries from [rkbin `a92d5e7`](https://github.com/rockchip-linux/rkbin/tree/a92d5e7df36cd1fac4bab24bc953b145fc0159a1). They are not covered by this project's MIT license. Rockchip's repository license permits binary redistribution; whether it explicitly covers these older, since-removed files is not stated, and the same files ship in common images for this board. See `firmware-NOTICE.txt` and `firmware-LICENSE.txt`. The boot chain is not blob-free.
- Buildroot 2025.02 with glibc, BusyBox and Dropbear, running from an initramfs in RAM.
- The C++17 framebuffer chat application and PrismML's MIT-licensed [`llama.cpp` fork](https://github.com/PrismML-Eng/llama.cpp), pinned to `5628c7338963b00a598f2a588fd09a79af6d70db`.
- The local ARMv8.0 NEON Bonsai dot-product patch for Q1_0, PQ2_0 and PTQ1_0 formats. It targets the Cortex-A35 without requiring dot-product or i8mm instructions.
- A raw Rockchip bootloader area, 128 MiB FAT32 boot partition, 512 MiB swap partition and an initially empty FAT32 data partition that grows on first boot.

**No model is included.** The configured default is PrismML's [Ternary-Bonsai-2-2B](https://huggingface.co/prism-ml/Ternary-Bonsai-2-2B-gguf), based on [Qwen/Qwen3.5-2B](https://huggingface.co/Qwen/Qwen3.5-2B) and licensed under Apache-2.0; the configured filename is `Ternary-Bonsai-2-2B-PTQ1_0.gguf`. Download models separately from their publisher and check their licenses.

## Performance

On-device `llama-bench` measurements with four threads compared the clean PrismML pin with the `0001` NEON patch. Mean generation throughput rose from 1.04 to 1.46 t/s (+40%) for Bonsai-1.7B Q1_0, 1.26 to 1.40 t/s (+11%) for Ternary-Bonsai-1.7B PQ2_0, and 0.83 to 0.92 t/s (+11%) for the default Ternary-Bonsai-2-2B PTQ1_0. These measurements do not include later optimizations.

In a separate sustained sweep of the default model using the installed engine, `cpu_mode=performance` and four threads gave the highest average throughput, 0.843 t/s, at a sampled peak of 82.7 °C, with thermal throttling. The same thread count in `saver` averaged 0.615 t/s at 72.5 °C, without thermal cooling. The shipped defaults remain `performance` and four threads. See the [benchmark methods and results](https://github.com/0bAndyWirus/r36llm/blob/v0.1.0/docs/benchmarks.md) for conditions and limitations.

## Optional features

- **Optional English/French output filter:** Set `output_keep=/data/r36llm/output-keep-en-fr.txt` for the default PTQ1_0 model. It retains 133,951 of 248,320 output tokens while leaving the full input vocabulary intact. It targets English/French prose and Markdown, not code output; preserved byte tokens can still form other text. On a hot sustained device run, decode increased from 1.058 to 1.122 t/s (+6.0%); peak RSS rose 1.5 MiB rather than falling. Kept logits were bit-identical in native x86 checks.
- **Prompt-cache TTFT:** Enabled by default. The app publishes the first sampled token before decoding the next one and avoids clearing buffers immediately overwritten by a snapshot restore. In one ordered device pair with the default model, four threads and seed 42, TTFT fell from 20.508 to 18.553 seconds (9.5%), excluding model load. Native checks produced byte-identical output over 20 turns. The single device pair does not isolate all thermal or frequency effects.
- **Two-row NEON kernels:** Enabled by default. Device decode improved from 0.9334 to 1.1217 t/s (+20.17%) for PTQ1_0 and 1.4069 to 1.5869 t/s (+12.79%) for PQ2_0 compared with `0001`. Cortex-A35 QEMU checks found 307,968 bit-identical comparisons per compiler with GCC 12.2 and Buildroot GCC 13.4.

## Download and flash

**Use a second microSD card** (at least 1 GB; 4 GB or more leaves room for models) and keep the card that came with your handheld untouched, so you can switch back at any time. If you must reuse the original card, make a full image backup of it first (for example with Win32 Disk Imager's "Read", or `dd` on Linux/macOS). **Flashing replaces the entire card's partition table and erases its contents. Never select an internal PC disk.**

Download `r36llm.img.xz` and `SHA256SUMS` from the same release into the same directory. Download or check out this repository at `v0.1.0` for the helper script. A checksum detects corruption; it does not authenticate an untrusted download source.

### Windows PowerShell helper

Preview eligible disks without writing:

```powershell
.\scripts\flash.ps1 -ImagePath .\r36llm.img.xz -WhatIf
```

Then open PowerShell **as Administrator**, check the reader's disk number, and run (replace `2` with your SD card's number):

```powershell
.\scripts\flash.ps1 -ImagePath .\r36llm.img.xz -DiskNumber 2
```

The helper requires you to type the disk number again before erasing anything. It checks `SHA256SUMS` when present, refuses boot/system/pagefile/BitLocker disks, locks and dismounts existing volumes, and writes and hashes the image range back from the target. It only offers USB/SD/MMC disks smaller than 256 GB; `-Force` relaxes only the size limit. It refuses to proceed if it cannot establish a disk's BitLocker safety state. The image requires a reader exposing 512-byte logical sectors.

For `.img.xz`, install `xz.exe` or `7z.exe` on `PATH`, or extract the `.img` first. The helper streams decompression into a temporary file before opening the disk, so allow enough space in `%TEMP%` for the uncompressed image. Keep `SHA256SUMS` beside the original compressed download and pass that `.img.xz` to the script to verify the release checksum. An extracted `.img` has different bytes and needs its own matching manifest entry.

For a locally built image, omit `-ImagePath` to use `out/bsp/artifacts/r36llm.img`. `-WhatIf` never opens a physical disk for writing, dismounts volumes or changes disk state. With a selected disk it can still read/hash the input and decompress into TEMP during preflight. The hidden `-TargetPath` parameter is only for developer tests against a new file in TEMP, never for flashing.

### balenaEtcher

Verify the compressed file against its `SHA256SUMS` entry, then use [balenaEtcher](https://etcher.balena.io/) to select `r36llm.img.xz`, choose the whole SD card and flash it. Wait for Etcher's write verification to finish. If extracting first, verify the original compressed download before extraction.

Safely eject the completed card, insert it into the specified handheld and power on.

## First boot

**Boot once before copying models or other files onto the card.** On the first boot, initialization checks the release disk signature and partition labels, expands partition 3 to fill the card except for the final 1 MiB, and formats its initially empty FAT32 filesystem. It refuses to erase a data partition containing files other than the release marker. Keep power connected and wait for initialization to finish; the boot-partition marker allows an interrupted initialization to resume.

The OS mounts the data partition at `/data`, creates `r36llm/models`, `logs`, `ssh` and `bin`, and copies default settings and prompts if missing. Boot diagnostics go to `/data/r36llm/logs/boot.log` when the data partition is mounted. The preformatted 512 MiB swap partition is enabled by the `swap_p2=1` default. The chat application starts without a bundled model; add a GGUF before expecting inference to work.

After initialization, shut down safely and put the card back in the PC. Copy your GGUF into `R36DATA:\r36llm\models\` using the actual Windows drive letter, and edit `r36llm/config.ini` if its filename differs from the default. Alternatively, use SSH over a USB Ethernet adapter after securing access. FAT32 limits each file to less than 4 GiB.

### Default credentials — change before networking

The default account is **`root` with password `r36llm`**. Change it before attaching the device to an untrusted network. The USB Ethernet connection uses device address `10.36.0.1`. Release-mode builds do not generate or embed the builder's personal SSH authorization key. Do not redistribute a personal image containing credentials, host keys or private data.
